# InstaBlock

Blocks Instagram and TikTok video traffic on iOS / iPadOS with a **local learn-and-shape VPN**: a packet-tunnel extension intercepts DNS lookups for Instagram's media CDN domains, learns the addresses they resolve to, and either black-holes them or throttles them to a trickle — so video stalls even from Instagram's cached IPs (while photos, which are small, still load), and everything else works normally. No external server, no DNS service dependency — everything runs on-device.

## How it works

- **Packet tunnel as split-DNS interceptor** (`InstaBlockTunnel/PacketTunnelProvider.swift`): the tunnel claims no default route — its only fixed route is a fake DNS server IP (198.18.0.53, RFC 2544 benchmark range). `NEDNSSettings.matchDomains` sends *only* queries for the blocked domains to that server. All other DNS and all other traffic never enter the tunnel.
- **Learn-and-shape**: each intercepted query is forwarded to the network's real resolver (discovered via libresolv, `ResolvShim/`); the answered A/AAAA addresses are learned, and the real answer is handed back to the client (NXDOMAIN only if every upstream fails). Every learned IP is added as a /32 (/128) route into the tunnel. Traffic arriving for those addresses is relayed — UDP (QUIC) through a per-host token bucket capped at **150 kbps** (384 KB burst), TCP dropped. The rate was tuned on-device: 150 kbps is the sweet spot where photos load and video stalls (`BlockController.throttleKbps`; the tunnel still accepts a `rate:<kbps>` message if you want to experiment). Photos and videos share the same hosts, so bandwidth is the only lever that separates them without decrypting TLS — photos survive a slow link, video stalls. The learned set and rate persist. DNS answers are returned to the client only *after* the new routes are in place, so Instagram can never connect to a CDN address the tunnel doesn't own. The relay's own sockets are pinned off the tunnel interface (`prohibitedInterfaceTypes`) to avoid a route loop.
- **Why both**: packet captures showed Instagram resolves its CDN hosts via system DNS, but races each lookup against a *persisted last-known-IP cache* — when DNS returns NXDOMAIN, the cached IP wins and video plays. Blackholing the learned IPs kills that path too (routes apply to already-open flows), so the block converges within one session.
- **Blocked domains** (`TunnelBlocker.blockedDomains`, authoritative copy in the provider): two policies. **Throttle** (Instagram — `fbcdn.net`, `cdninstagram.com`, incl. the ISP-hosted `*.fna.fbcdn.net` cache nodes): photos and videos share these hosts, so traffic is capped rather than cut. **Drop** (TikTok — `tiktokcdn.com`, `tiktokcdn-us.com`, `tiktokcdn-eu.com`, `ibytedtos.com`, `bytefcdn-oversea.com`, `byteicdn.com`, `bytedance.map.fastly.net`): all video, and its short low-bitrate clips slip through a throttle, so traffic to these hosts is dropped outright. The policy is chosen per learned IP from the DNS question name. Each entry covers all subdomains. Meta's API hosts (`*.c10r.*`) are not blocked; TikTok's Fastly nodes serve the API from the same IPs as the video CDN, so the TikTok feed stops loading too — inherent to blocking an all-video app.
- **Always-on blocking**: every launch/foreground pass re-asserts the VPN config with on-demand rules, so the tunnel reconnects automatically on any network. There is no off switch; removing the app (or its VPN config in Settings) is the only way out.
- **Timed break** (5/15/30 min): the app sends `break:<unix-time>` to the running tunnel, which withdraws the learned routes (media flows directly) and restores them from its **own in-process timer** when the break ends — the VPN never disconnects, so re-blocking doesn't depend on the app running while you're in Instagram. The break end also persists inside the extension, surviving tunnel restarts. The app keeps the countdown UI, a local notification at expiry, and re-syncs the break state on every foreground activation.
- **Diagnostics**: `tools/capture-instagram.sh` mirrors the phone's traffic over USB (rvictl + tshark) and `tools/summarize-capture.py` reports DNS provenance, SNI, QUIC handshakes, and top hosts — the tooling that drove the design above.

## Why not NERelay?

The first implementation used `NERelayManager` with an unreachable relay (`matchDomains` → blackhole). It worked for standard-stack traffic (verified in Safari), but the Instagram app's in-house networking stack bypassed hostname-based relay matching and streamed video anyway. DNS-level blocking was verified effective against Instagram, hence the pivot. The relay code remains in `RelayBlocker.swift`; the app removes any leftover relay config on first run after migration.

## Requirements / caveats

- **Real device required** — NetworkExtension doesn't function in the Simulator (the UI runs there via stubs).
- First run shows the system's **"Would Like to Add VPN Configurations"** prompt — tap Allow. If "Don't Allow" is ever tapped, iOS remembers and every save fails with `NEConfigurationErrorDomain Code=10 "permission denied"` until the app is deleted and reinstalled.
- Entitlements: app has `packet-tunnel-provider` (+ legacy `relay`); the extension has `packet-tunnel-provider`. Automatic signing with a paid team handles provisioning.
- The VPN badge shows in the status bar while blocking is active, and the config is visible in Settings → VPN.
- Instagram holds long-lived QUIC connections and caches media — after config changes, force-quit Instagram (and briefly toggle airplane mode) before judging whether blocking works.
- Blocking `fbcdn.net`/`cdninstagram.com` also affects Instagram photos and other Meta-family media (WhatsApp/Facebook CDN assets ride the same hosts).
